# Private beta — Telegram Stars dedicated test network

Scope: non-commercial Telegram provider testing only. No genuine money, supplier content, live receipt, commercial subscription or production VIP authority. `financial_authority=NONE` remains true. This procedure does not report an unexecuted test as accepted.

## Account and network separation

The normal Telegram BOT private beta and Telegram's dedicated Stars test network are different environments. A normal BotFather token plus an empty `provider_token` does **not** make a payment free or simulated.

Create a **Telegram test-server user account**, then create a **separate bot using BotFather in that test environment**. Official client access instructions are in [Testing your bot](https://core.telegram.org/bots/features#testing-your-bot), checked 2026-10-26. All payment requests must use the fixed `https://api.telegram.org/bot<TOKEN>/test/METHOD_NAME` route. The server module has no production payment endpoint and accepts no arbitrary host or method. Existing real-conversation bot credentials must never be substituted automatically.

Configure the test bot token and a distinct webhook secret through protected staging secrets, never chat, public configuration, logs or a browser bundle. Record the test account/bot identity, private test chat/channel and consenting test-user numeric IDs in the reviewed server-owned beta binding. Telegram usernames are not identity or consent evidence. Dedicated test identities can differ from their main-network identities.

## Activation prerequisites

1. Verify the exact protected release SHA and the staging target before loading secrets. Verify owner/MFA authorization, active private-beta tenant, current participant consent, test-network bot binding, a private destination and allowed method/count/window controls.
2. Apply the reviewed additive `20261026101723_private_beta_stars_test.sql` migration through the approved staging release. `createTelegramStarsUatFromDatabase` wires committed unique attempt/effect keys, persisted request count, nonce custody, unresolved-effect fencing, append-only outcomes and audit. Capability maps supplement PostgreSQL custody; they cannot reset it after restart.
3. Supply `readAuthenticatedBinding` from the authenticated server authority read. A manually supplied JSON document, environment flag or TypeScript interface is insufficient. Verify `getMe` on the fixed `/test/` endpoint and the exact configured numeric bot ID before issuing a session capability.
4. Explicitly set a **test-only integer XTR amount** in the server-owned test binding. The `POLAT_VIP_30D_DRAFT` reference retail target of69.00USD is not an approved XTR price or exchange rate. Null/missing price blocks an invoice. No live invoice is authorized by a draft.
5. The new private immutable TEST receipt/delivery mapping preserves `TELEGRAM_DEDICATED_TEST` provenance and atomically feeds the existing TEST subscription engine. A database trigger rejects legacy simulation snapshots for these invoices. The real `private.verified_payment_receipts` writer and trusted live `payment.confirmed` event remain unavailable. Configure a dedicated private TEST channel and its verified source hash separately; an unset channel blocks access effects.

## Executable acceptance sequence

Use one invited test identity and one reviewed test invoice first. Set exact permitted operations and bounded request counts in the activation record; do not activate a global campaign or worker.

1. Call the server-only connection function with protected credential access, authenticated binding reader, durable custody and the fixed HTTPS transport. Retain sanitized bot ID, release/binding revision and committed attempt identity. No secret/header/raw body enters the audit record.
2. Build a private single-chat invoice with currency`XTR`, `provider_token=""`, one integer price and the immutable `uat-stars:<invoice UUID>` payload. `sendInvoice` must return a matching private-chat message ID/currency/amount. A network timeout, malformed response or wrong target is UNKNOWN; do not retry blindly.
3. Authenticate the incoming webhook with the separate secret header. Match payer/chat numeric identity, amount, currency, invoice payload and current binding. Answer pre-checkout within Telegram's10-second deadline. Pre-checkout acceptance is **not** a receipt or an entitlement.
4. Observe the actual authenticated `successful_payment`, retain its exact charge identity privately and independently query `getStarTransactions` on the same test bot. Correlate charge ID, incoming direction, payer, amount, invoice and source time. A stale, incomplete, conflicting or missing ledger observation remains pending/review. Bounded pages contain at most25 entries; a full page or non-first page does not prove complete history.
5. The existing session’s `recordTestEvidence` consumes only its own opaque authenticated callback and independent ledger capabilities. It commits the private TEST receipt/delivery, `payment.test_observed`, existing TEST invoice and fixed30-day subscription period atomically. Global bot/charge/kind uniqueness prevents cross-tenant reuse. No genuine `payment.confirmed` is emitted. Refund-before-payment, conflicting delivery facts, stale control and incomplete ledger remain held. Distinct callback deliveries for one operation are retained without creating another period.
6. Call `prepareTestAccess(invoiceId)` only after the TEST payment is recorded, then `processNextTestAccess(commandPrefix)` for one bounded existing-queue lease. The fixed `/test/` adapter checks the private channel and bot rights, creates an expiring join-request invite, records its raw link privately and exposes only a `test:invite:<hash>` in public access records. Its fixed TEST-only invite notice goes only to the verified test user. `receiveTestJoinRequest` queues the existing join operation; a matching actual `/test/getChatMember` is required before MEMBER. Refund/expiry queues a revoke; matching ban acknowledgement plus left/kicked membership is required before REVOKED. Unknown effects/expired leases remain FAILED+REVIEW and are not automatically replayed. The legacy fake worker cannot claim or complete these dedicated TEST jobs. Existing LIVE kill switches remain unchanged; no supplier signals are delivered.
7. Request a full test refund using the original payer and charge ID. `refundStarPayment=true` acknowledges a request; retain the outgoing ledger/refund update before asserting refund completion. Incoming and refund transactions can share the same Telegram charge ID, so operation identity includes direction/kind. Refund-before-payment stays pending. Duplicate callbacks must not create a second movement or period.
8. Verify final TEST state, no genuine receipt/event/LIVE subscription/access rows, unchanged production controls and an auditable history. Report exact real-provider attempts and actual outcomes separately from mock tests. Retain failures and unknown results.

The TEST-only recorder, existing subscription consumer integration, dedicated TEST VIP adapter, authenticated route and Edge relay are implemented. They are not registered in the general LIVE payment/entitlement worker. No actual provider call, hosted migration or deployment is implied by these files. Disposable PostgreSQL and injected HTTP acceptance are separate from genuine Telegram TEST acceptance.

## Required negative cases

Wrong network/token/bot/payer/chat/tenant/invoice/currency/amount; unapproved/missing price; duplicated/escaped JSON keys; unsafe integer/notation; expired invoice; recurring payment; duplicate delivery; same charge claimed in another tenant; duplicate or conflicting ledger rows; refund before original payment; malformed/partial/oversized body; timeout, cancellation,429 and5xx; permission loss; stale consent/binding; forged/copied capability; interrupted or unknown durable result; concurrent/restarted attempts. No test removes an audit or converts UNKNOWN into success.

Deploy only the reviewed `polat-private-beta-stars-ingress` Edge function with JWT verification disabled for **that function alone**, keeping its Telegram secret check and independent Stars-domain HMAC. Configure Edge secrets `POLAT_UAT_STARS_TEST_WEBHOOK_SECRET`, `POLAT_UAT_STARS_RELAY_SECRET` and the existing project-scoped `POLAT_UAT_VERCEL_BYPASS` custody. The upstream is hardcoded to `https://gold-revenue-os-staging.vercel.app/api/webhooks/private-beta-stars`. Admin SSO and application authentication remain enabled. Register this Edge URL only with the dedicated `/test/setWebhook`, never with the normal beta bot.

`private.private_beta_stars_control_record` is postgres-only protected release custody: actual `/test/getMe` numeric bot/source hash, approved test integer XTR amount, verified separate test-user/customer/consent mapping, exact program generation/window and optional private test-channel/source hash. It cannot be called by the application/browser role. Missing control, credentials, test price or channel stays BLOCKED. The amount cannot change after dispatch starts; request count never resets on refresh.

The authenticated Stars webhook never creates an invoice or model call. Use the server-only database factory’s `createInvoice(approvedOfferId, commandId)` followed by `sendInvoice` for one explicitly approved fictional test offer. Ordinary TEST `/start`/text updates are ignored. Ingress stores source hash and durable update identity before dispatch; duplicates never repeat API effects. Pending/unknown processing is visible in the existing private-beta operator notes/audit rather than being reported as successful.

The expected genuine StageG sequence is `createInvoice → sendInvoice → precheckout webhook → successful-payment webhook → independent ledger → recordTestEvidence → prepareTestAccess → processNextTestAccess → authenticated join webhook → matched membership → test refund → matched refund ledger → revoke → matched membership`. Expiry/recovery can be driven using the existing bounded TEST maintenance then the dedicated TEST access processor. No API credential, actual TEST price, TEST bot/account/channel or provider result was invented or configured by the offline acceptance.

Founder entry point: `POST /api/v1/admin/private-beta/stars-test-invoice`, same-origin form with exactly `program_id`, `approved_offer_id`, `command_id` UUID fields. The selected tenant comes from the authenticated Admin session. The SQL scope check requires the program owner, super_admin role and fresh verified TOTP AMR (five minutes); a refreshed JWTiat is not a new MFA challenge. It checks the current TEST control before credential loading. No client-supplied tenant, payer, chat, price, credential or approval boolean is accepted. A repeated command with an existing invoice returns a review state without sending it again. An invoice ACK is explicitly `receipt_created=false`, not payment or VIP activation. Missing price/account/control/MFA or unknown send returns BLOCKED/REVIEW with `retry=NONE`. GET never creates an invoice.
